# 'PDF-to-Workbook' (BYOC 문제집 디지털화 앱) 아키텍처 & 사업 타당성 설계

> 대상: 1인 개발/운영 체제의 에듀테크 SaaS
> 핵심 전제: 콘텐츠를 직접 제공하지 않는 **도구형(Tool) 플랫폼** — 사용자가 소장한 PDF/사진을 "가공"만 해준다.

---

## 1. 저작권법 제30조 & OSP(플랫폼 면책) 아키텍처

### 1.1 법적 포지셔닝의 핵심 원칙

저작권법 제30조(사적 이용을 위한 복제)는 **"영리를 목적으로 하지 아니하고"** 개인이 복제하는 경우를 전제로 한다. 문제는 우리가 "영리 플랫폼"이라는 점이다. 따라서 방어 논리는 다음과 같이 구성해야 한다.

- **"누가 복제하는가"의 재정의**: 서비스는 콘텐츠를 복제·배포·전송하는 주체가 아니라, **사용자가 이미 소지한 파일에 대해 사용자 본인의 사적 복제 행위를 대행하는 도구**라는 프레이밍이 핵심이다. 클라우드 스토리지(Dropbox, Google Drive)나 문서 변환기(PDF→Word 변환 SaaS)가 저작권 침해 책임을 지지 않는 것과 동일한 논리 구조.
- **온라인서비스제공자(OSP) 책임제한 (저작권법 제102~103조)**: 한국 저작권법은 미국 DMCA와 유사한 **notice-and-takedown** 구조의 OSP 면책 규정을 두고 있다. 다음 4대 요건을 기술적으로 실제 구현해야 실질적 면책이 인정된다.
  1. 침해 사실을 인지하지 못했음(구조적으로 인지 불가능하게 설계)
  2. 인지 즉시 삭제/차단 조치 가능한 시스템(관리자 콘솔의 즉시 삭제 기능)
  3. 반복 침해자 계정 정지 정책 존재 및 실행 기록
  4. 침해 신고 접수 채널(저작권 침해 신고 페이지, 이메일) 상시 운영

### 1.2 테넌트 격리 구조 (Tenant Isolation)

가장 중요한 것은 **"교차 열람/재사용이 구조적으로 불가능함"을 코드와 DB 스키마로 증명**하는 것이다. 이는 법적 방어의 핵심 증거가 된다.

```
┌─────────────────────────────────────────────────────────┐
│  Storage Layer (R2/S3) — Per-User Prefix 강제             │
│  bucket/{user_id}/{document_id}/pages/{page_no}.enc      │
│  bucket/{user_id}/{document_id}/derived/{bbox_id}.json   │
└─────────────────────────────────────────────────────────┘
                          ▲
                 (서버조차 user_id 없이는 접근 경로 생성 불가)
┌─────────────────────────────────────────────────────────┐
│  DB Layer — Row-Level Security 강제 (Postgres RLS)        │
│  documents.user_id = current_setting('app.user_id')      │
│  → 애플리케이션 버그로도 타 사용자 데이터 접근 불가         │
└─────────────────────────────────────────────────────────┘
```

- **원본 파일은 사용자별 격리된 버킷 prefix + 개별 사용자 대칭키(envelope encryption, 예: AWS KMS/R2 커스텀 헤더)로 암호화 저장.** 서버 운영자 본인도 대량 조회 스크립트를 돌리지 않는 이상 "구조적으로" 열람이 어렵게 설계 — 이것이 "OSP가 침해를 조장/방치하지 않았다"는 핵심 증거.
- **파생 데이터(문항 bbox, 추출 텍스트, LaTeX)도 동일한 user_id 파티션 내에서만 저장.** 절대 전역 공유 캐시에 넣지 않는다 (아래 1.3 참조).
- **DB는 Postgres RLS(Row Level Security)를 애플리케이션 레벨 필터링과 별개로 DB 엔진 자체에서 강제**한다. Supabase/RDS 모두 지원. 이는 "개발자의 실수로 인한 교차 노출"조차 구조적으로 막는다는 것을 의미하며, 소송 시 "기술적 상당한 주의(due diligence)를 다했다"는 증거로 제출 가능하다.

### 1.3 "중복 파일 해시 공유 금지" 원칙 — 가장 위험한 유혹을 차단

원가 절감을 위해 "동일 문제집(천재교육 중1-1 쎈 수학)을 여러 사용자가 업로드하면 이미 처리된 결과를 재사용"하고 싶은 유혹이 반드시 생긴다. **이것이 바로 저작권 소송에서 가장 치명적인 지점이다.** 해시 기반 재사용 = 사실상 콘텐츠 데이터베이스를 구축해 전 사용자에게 배포하는 것과 법적으로 동일시될 위험이 매우 크다 (마치 "1명이 구매한 책을 스캔해서 만인에게 나눠준" 구조가 되어 제30조의 "사적 이용" 전제 자체가 무너짐).

**설계 원칙 (반드시 지킬 것):**
- 파일 해시(SHA-256)를 **부정행위 탐지(동일 파일 대량 업로드 등 이상 패턴 감지)** 목적으로만 내부 로깅하고, **처리 결과(bbox, OCR 텍스트, LaTeX)의 사용자 간 공유·캐시 재사용에는 절대 사용하지 않는다.**
- 유일하게 허용되는 재사용 최적화는 "**동일 레이아웃 템플릿의 기하 정보(페이지 여백, 컬럼 구조 같은 구조적 메타데이터)**"뿐이며, 이마저도 텍스트/문항 내용은 전혀 포함하지 않는 순수 좌표 정보로 한정한다. 애매하면 아예 하지 않는다 — 비용보다 법적 리스크가 크다.
- 각 사용자의 처리 파이프라인은 **처음부터 끝까지 독립 실행**되어야 하며, 이는 코드 레벨에서 "글로벌 콘텐츠 캐시 테이블"이 존재하지 않는다는 것으로 증명 가능해야 한다.

### 1.4 필수 약관(Terms) 설계 — Safe Harbor 조항

이용약관에 아래 조항을 명시적으로 포함하고, **업로드 시점에 체크박스(단순 스크롤 동의 아님) 형태로 재확인**받아야 한다.

1. **소유 확인 조항**: "본인이 합법적으로 구매/소장한 교재에 한하여 업로드하며, 제3자 저작권을 침해하는 콘텐츠(스캔본 재배포물, 불법 다운로드 파일 등)를 업로드하지 않는다"는 확약. 위반 시 즉시 계정 정지 및 콘텐츠 삭제.
2. **비배포 확약**: 변환된 디지털 문제 카드/오답노트 PDF를 본인 및 직계 가족(다자녀 프로필) 외 제3자에게 배포·전송·판매하지 않는다는 조항. (서비스 자체가 배포를 지원하지 않도록 "공유 링크 생성" 기능은 만들지 않는다 — 기능 자체를 없애는 것이 최고의 법적 방어.)
3. **면책 및 책임 소재 조항**: 업로드 콘텐츠의 저작권 적법성에 대한 책임은 전적으로 사용자에게 있으며, 플랫폼은 저작권 침해 신고 접수 시 즉시 삭제 조치를 취할 권리와 의무를 갖는다는 OSP 면책 문구.
4. **DRM/워터마킹**: 생성된 재시험지 PDF에 "본인 학습용, 재배포 금지 / {user_id 뒷 4자리} 발급" 같은 워터마크를 삽입 — 법적 효력보다는 **재배포 억제 심리적 장치 + 유출 추적 수단**으로서의 실무적 가치가 크다.
5. **출판사 대응 채널**: `copyright@서비스도메인` 신고 접수 페이지를 반드시 운영하고, 저작권법 제103조 절차(권리주장 접수 → 즉시 접근 차단 → 복제·전송자에게 통지)를 그대로 구현한 관리자 워크플로우를 갖춰둔다. 실제로 출판사가 문제 제기를 해올 경우 "24시간 내 삭제" 같은 SLA를 공개적으로 표방하면 우호적 협상 카드가 된다.

**리스크 총평**: 완전한 면책은 불가능하나, 위 구조(격리·암호화·비공유·즉시삭제)를 실제로 구현해두면 "실질적으로 사적 복제 대행 도구"라는 주장의 신빙성이 크게 올라가고, 최악의 경우에도 소송이 아닌 "삭제 요청 대응" 수준으로 리스크를 낮출 수 있다.

## 2. 비용 최적화 DLA(문서 레이아웃 분석) + OCR 파이프라인

### 2.1 왜 비전 LLM 단독 처리가 안 되는가

200페이지 문제집을 GPT-4o/Gemini에 페이지 이미지로 직접 넣으면, 페이지당 High-res 이미지 토큰(~1,500~3,000 토큰) + 응답 토큰까지 페이지당 수십 원 수준의 비용이 발생하고, 200페이지 × 수천 명 사용자 = 감당 불가능한 원가 구조가 된다. 특히 "레이아웃 파악"이라는 상대적으로 단순한 작업에 범용 비전 LLM의 추론 비용을 쓰는 것은 근본적으로 낭비다.

### 2.2 2단계 파이프라인 설계

```
[Stage 0] 전처리 (Preprocessing) — 서버리스, 초저가
  ├─ PDF는 pdf2image/PyMuPDF로 페이지당 이미지 렌더 (150-200 DPI)
  ├─ 사진 촬영본은 OpenCV 기반 자동 crop/deskew(기울기 보정)/perspective correction
  └─ 이미지 이진화 및 노이즈 제거 (adaptive threshold)

[Stage 1] 경량 레이아웃 검출 (Document Layout Analysis)
  ├─ 모델: YOLOv8/YOLOv10 fine-tuned on DocLayNet (or PP-DocLayout, LayoutLMv3 detector head)
  ├─ 역할: 페이지를 "문항 번호, 지문/보기, 본문, 수식 영역, 정답표, 표/그림" 등
  │        클래스별 Bounding Box로만 분할 (텍스트 인식은 안 함)
  ├─ 실행 환경: GPU 서버리스 (Modal.com, RunPod Serverless, AWS Lambda+EFS 등)
  │        — 상시 GPU 서버 대신 요청 시에만 콜드스타트, 유휴 시 $0
  └─ 비용: 페이지당 GPU 추론 0.1~0.3초 수준 → 0.1~0.3원/페이지 목표

[Stage 2] 선택적 정밀 OCR (필요 영역만)
  ├─ 일반 텍스트 영역: Surya OCR / PaddleOCR (오픈소스, 자체 호스팅)
  │        — 한국어 인식률 우수, GPU 1장으로 페이지당 초 단위 처리
  ├─ 수식 영역만: LaTeX-OCR (pix2tex) 또는 Google Document AI Math OCR
  │        — 수식은 전체 페이지의 5~15%만 차지 → 이 영역에만 특화 모델 적용
  ├─ 애매하거나 신뢰도 낮은 영역만 비전 LLM으로 에스컬레이션
  │        (예: OCR confidence < 0.7인 영역만 GPT-4o-mini/Gemini Flash로 재확인)
  └─ 비용: 페이지의 90%는 오픈소스 처리, 10% 미만만 LLM 호출
           → 페이지당 총 비용 1~2원 목표 달성
```

### 2.3 핵심 비용 절감 전략 3가지

1. **"검출과 인식의 분리"**: YOLO 계열은 "이 영역이 무엇인지"만 알아내고, 텍스트/수식 "내용"은 각 영역에 최적화된 전문 모델에게 위임. 범용 LLM은 최후 수단(fallback)으로만 사용.
2. **서버리스 GPU 콜드스타트 활용**: 상시 GPU 인스턴스(월 $200~500)를 켜두지 않고, Modal/RunPod의 "요청당 과금 + 자동 슬립" 모델을 사용하면 1인 서비스 초기 트래픽에서 고정비를 거의 0으로 만들 수 있다. 배치 작업(사용자가 업로드 후 비동기로 기다리는 구조라 실시간성 요구가 낮음)이라 콜드스타트 5~10초 지연은 허용 가능.
3. **해상도 계층화**: 레이아웃 검출은 저해상도(150 DPI)로 충분, 실제 OCR이 필요한 crop 영역만 원본 고해상도로 다시 잘라내어 처리 — 전체 페이지를 매번 고해상도로 다루지 않음으로써 추론 시간과 비용을 동시에 절감.

### 2.4 파이프라인 오케스트레이션

```
Upload → Object Storage (R2) 저장
   → Queue Job 등록 (BullMQ/Redis)
   → Worker: Stage 0 전처리
   → Worker: Stage 1 레이아웃 검출 (GPU serverless 호출)
   → Worker: Stage 2 영역별 OCR (오픈소스 우선, 저신뢰도만 LLM)
   → 결과를 문항 단위 JSON(bbox + text + LaTeX + type)으로 DB 저장
   → 사용자에게 "변환 완료" 알림 (웹푸시/이메일)
```

## 3. 정답지 매핑 & 자동 채점 로직

### 3.1 "빠른 정답표" OCR 파싱 팁

시중 문제집 정답표는 대체로 다음 두 형태 중 하나다.

- **표 형태** (예: 1열=번호, 2열=정답, 격자형 다단 배열): OpenCV로 표 선(line) 검출 → 셀 단위 분할 → 셀별 OCR. PaddleOCR의 `PP-Structure` 표 구조 인식 모듈이 이 용도에 최적화되어 있음.
- **인라인 텍스트 형태** (예: "1.③ 2.① 3.해설참조 4.②..."): 정규식 기반 패턴 매칭이 표 인식보다 훨씬 안정적. `\d+\.\s*([①-⑤]|[1-5]|[가-마])` 같은 패턴으로 번호-정답 페어 추출.

**핵심 팁**: 정답표는 "문항 번호의 연속성"이라는 강력한 사전 지식(prior)이 있다. OCR이 번호를 34로 오인식해도 앞뒤 문맥(33, 35)이 있으면 **번호 시퀀스 검증 로직(등차 1 증가 여부 체크)**으로 자동 보정 가능 — 이것만으로 정답표 매핑 정확도를 크게 끌어올릴 수 있다. 배점 정보가 있다면 "총점 100점 검증"으로 배점 합계 크로스체크도 가능.

### 3.2 30초 검수 UI 설계

OCR 오인식은 필연적이므로, "완벽한 자동화"가 아니라 **"사람이 빠르게 틀린 것만 고치는" UX**가 핵심이다.

```
┌───────────────────────────────────────────────────┐
│  정답 검수 (전체 42문항 중 3개만 확인 필요)          │
│                                                     │
│  ⚠️ 낮은 신뢰도 항목만 자동으로 상단에 노출          │
│  ┌─────────────────────────────────────────────┐  │
│  │ 문항 17   OCR 인식: "③"  (신뢰도 62%)         │  │
│  │ [①] [②] [●③] [④] [⑤]   ← 한 탭으로 정정      │  │
│  └─────────────────────────────────────────────┘  │
│  ┌─────────────────────────────────────────────┐  │
│  │ 문항 29   OCR 인식: "정답 없음" (신뢰도 낮음)  │  │
│  │ [텍스트 직접 입력: ______]                     │  │
│  └─────────────────────────────────────────────┘  │
│                                                     │
│  ✅ 나머지 39문항 (신뢰도 95%+) — 자동 확정됨        │
│  [펼쳐서 전체 보기 ▾]                               │
│                                                     │
│              [ 확인 완료 → 채점 시작 ]              │
└───────────────────────────────────────────────────┘
```

- **신뢰도 기반 필터링이 핵심**: OCR 엔진이 반환하는 confidence score를 기준으로 95% 이상은 자동 확정하고 화면에서 숨긴다. 사람은 낮은 신뢰도 항목(보통 전체의 5~10% 이내)만 본다 — 이것이 "30초 검수"를 가능케 하는 유일한 방법.
- **원클릭 정정**: 객관식은 텍스트 입력 대신 버튼 탭 1회로 정정 가능하게 (모바일 친화적).
- **문항 이미지 썸네일 동시 노출**: 정답표 텍스트만 보여주면 검증이 어려우므로, 해당 문항의 실제 페이지 crop 이미지를 함께 작게 보여줘 "이게 맞나?" 육안 확인이 가능하게 한다.
- **일괄 승인 옵션**: "나머지는 다 맞다고 가정하고 진행" 버튼으로 완벽주의를 요구하지 않는다 — 채점 후에도 개별 문항 정답은 언제든 재수정 가능하도록 설계(사후 수정 가능성이 사전 완벽 검수 부담을 낮춤).

## 4. 1인 개발자 추천 풀스택 기술 스택

| 영역 | 추천 | 이유 |
|---|---|---|
| **프론트엔드** | Next.js (App Router) + TypeScript | SSR/SSG로 SEO(오답노트 랜딩 등)와 성능 동시 확보, Vercel 배포로 인프라 관리 부담 0 |
| **태블릿 필기/캔버스** | `excalidraw`(오픈소스) 커스텀 또는 `perfect-freehand` + Canvas API | 손글씨 압력감 있는 획 렌더링에 특화, MIT 라이선스로 자유롭게 임베드 가능 |
| **상태관리** | Zustand 또는 React Query(TanStack Query) | 문항 카드 넘기기 같은 로컬 UI 상태는 Zustand, 서버 동기화(채점 결과 등)는 React Query로 역할 분리 |
| **백엔드 API** | Next.js API Routes 또는 별도 FastAPI(Python) | DLA/OCR 파이프라인이 Python 생태계(PaddleOCR, YOLOv8) 의존적이므로, API 서버는 FastAPI로 분리하고 프론트는 Next.js로 유지하는 구조 추천 |
| **비동기 큐** | BullMQ (Redis 기반) | Celery보다 Node.js 생태계와 통합이 쉽고, Next.js 백엔드와 동일 언어(TS)로 운영 부담 최소화. Redis는 Upstash(서버리스) 사용 시 인프라 관리 필요 없음 |
| **DB** | Supabase (Postgres) | RLS(1.2 참고)를 기본 제공, Auth/Storage/Realtime까지 한 서비스에서 해결 → 1인 운영에 최적. 다자녀 프로필 같은 관계형 데이터 모델링에도 적합 |
| **파일 스토리지** | Cloudflare R2 | S3 호환 API + **Egress 비용 없음**(트래픽 다운로드가 잦은 PDF/이미지 서비스에서 비용 차이가 큼) |
| **GPU 추론(DLA/OCR)** | Modal.com 또는 RunPod Serverless | 상시 GPU 서버 없이 요청당 과금, 자동 스케일 다운으로 유휴 비용 제거. Python 함수를 그대로 데코레이터로 배포 가능해 운영 부담 최소 |
| **결제** | 토스페이먼츠(TossPayments) | 국내 정기결제(빌링키) API가 국내 PG 중 개발자 경험이 가장 우수, 정산/부가세 처리도 상대적으로 간편. 구독+종량제 혼합 모델을 하나의 API로 처리 가능 |
| **인증** | Supabase Auth (또는 Clerk) | 소셜 로그인/이메일 인증을 자체 구현하지 않고 위임 |
| **알림** | Resend(이메일) + 웹푸시(OneSignal) | 변환 완료 알림처럼 비동기 작업 완료 통지에 필수, 무료 티어로 초기 운영 가능 |
| **모니터링/에러** | Sentry + Vercel Analytics | 1인 운영 시 장애를 빠르게 감지하는 것이 유지보수 비용을 줄이는 핵심 |
| **배치/크론** | Vercel Cron 또는 Supabase Edge Functions | 만료 구독 체크, 정리 작업 등 소규모 스케줄 작업에 별도 서버 불필요 |

**전체 아키텍처 요약**: `Next.js(FE+경량 API) ↔ FastAPI(DLA/OCR 워커, Modal 서버리스 GPU) ↔ Supabase(DB+Auth+RLS) ↔ Cloudflare R2(파일) ↔ 토스페이먼츠(결제)` — 이 조합은 상시 서버를 거의 두지 않고(Vercel/Supabase/Modal 모두 서버리스) 트래픽에 따라 비용이 선형적으로만 증가하는 구조라, 초기 무료 사용자가 많아도 고정비 부담이 낮다.

## 5. 온보딩 허들(업로드 마찰) 극복 전략

### 5.1 "즉시 가치 체험" 온보�딩 플로우

핵심 가설: **"내 책을 스캔해서 올리는 것"은 신뢰가 쌓이기 전 사용자에게는 너무 큰 첫 행동(Big Ask)**이다. 따라서 첫 행동은 업로드가 아니라 "샘플로 결과물을 먼저 보여주는 것"이어야 한다.

```
Step 1 (0클릭 체험) — 앱 진입 즉시
  └─ "지금 바로 체험하기" → 자체 제작/퍼블릭도메인 샘플 문제집
     (예: 교육부 공개 학습자료, 평가원 기출 공개본 등 저작권 이슈 없는 문항)
     이 즉시 카드 형태로 풀이 화면에 뜬다 (로그인/업로드 없이)

Step 2 (가치 확인) — 30초 이내
  └─ 문제 3~5개 풀이 → 자동 채점 → "오답노트 PDF 미리보기" 즉시 생성
     "이게 당신 책으로도 가능합니다" 메시지와 Before/After 비교 이미지

Step 3 (전환 유도) — 가치를 본 직후
  └─ "내 문제집으로 해보기" CTA → 이 시점에 카메라 업로드 유도
     스마트폰 카메라로 "책을 펼쳐서 찍기"만 하면 되도록 극도로 단순화
     (앱이 자동 crop/보정하므로 "잘 찍어야 한다"는 부담 제거 — 이 문구를 명시)

Step 4 (마찰 최소화 업로드 UX)
  └─ PDF 업로드보다 "카메라로 촬영" 경로를 기본값으로 우선 노출
     (PDF를 구할 수 있는 사용자는 이미 소수 — 대부분은 종이책 소지자)
  └─ 페이지를 한 장씩 찍을 때마다 실시간으로 "인식됨 ✅" 피드백
     (전체 업로드 후 결과를 기다리게 하지 않고, 촬영 즉시 성공 신호를 줌)
```

### 5.2 바이럴 요소 기획

1. **"다자녀 프로필" 자체가 바이럴 유닛**: 학부모는 첫째/둘째 자녀를 함께 관리하려는 니즈가 강함 → 무료 티어에서도 "프로필 추가"는 허용하되 "월 변환량"만 제한 → 자연스럽게 구독 전환 유도되면서도, 공유 계정 형태로 배우자를 초대하는 흐름을 만들면 자연 확산.
2. **결과물의 공유 가능성 활용 (콘텐츠가 아닌 "성과"를 공유)**: 오답노트 PDF 자체는 배포하면 안 되지만(1.4 참조), "이번 주 틀린 문제 5개 중 4개를 다시 풀어서 맞췄어요 🎉" 같은 **학습 성과 카드(이미지)**는 자녀의 저작권과 무관한 "우리 서비스가 만든 메타데이터"이므로 부모가 SNS/맘카페에 공유하기 좋게 디자인 — 이것이 실질적 바이럴 채널이 된다.
3. **맘카페/지역 커뮤니티 타겟 시딩**: 초기 사용자 확보는 "어떤 문제집이 잘 디지털화되는지" 실제 사용 후기가 신뢰를 만드는 카테고리이므로, 광고보다 커뮤니티 내 실사용 후기(예: "디딤돌 초등 수학 1-1로 해봤는데 인식률 좋았어요") 확산이 훨씬 효율적. 초기엔 파워유저에게 무료 구독 제공 후 후기 유도.
4. **"N회독 관리" 자체가 리텐션 겸 바이럴 훅**: 오답노트를 2주 뒤 자동으로 재알림("복습할 때가 됐어요")하는 기능은 재방문율을 높이는 동시에, 반복 사용 경험이 쌓일수록 "이 도구가 정말 효과 있다"는 입소문의 근거가 된다.

### 5.3 마찰 vs 신뢰의 트레이드오프 관리

무료 티어(1권/월 30페이지)는 "가치를 완전히 체감할 만큼 충분히 크게" 설정하는 것이 중요하다 — 너무 작으면(예: 5페이지) 가치 검증도 못 한 채 이탈하고, 너무 크면(예: 무제한) 전환 동기가 사라진다. **"자녀의 오답노트 한 단원 분량"에 해당하는 페이지 수**로 무료 한도를 설계하는 것을 권장 (보통 초등 수학 문제집 한 단원 = 20~30페이지 수준).

## 종합 우선순위 (1인 개발 로드맵 제안)

1. **MVP 최우선**: Step 2단계 파이프라인(YOLO 레이아웃 검출 + PaddleOCR) 없이 **비전 LLM 직접 호출로 먼저 검증** (초기 트래픽이 적을 때는 비용보다 속도가 중요) → 사용자 반응 확인 후 비용 최적화 파이프라인으로 전환.
2. **법적 안전장치는 MVP부터 필수**: 테넌트 격리와 "공유 금지" 원칙은 나중에 리팩터링하기 매우 어려우므로 **처음부터 설계에 반영**해야 한다.
3. **결제/구독은 사용자 100명 확보 후**: 초기에는 무료 체험으로 리텐션과 파이프라인 정확도를 먼저 검증하고, 유료화는 그 다음 단계로.
